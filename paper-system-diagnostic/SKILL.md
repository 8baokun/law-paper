# 应用法学论文系统诊断器

## 定位

本技能是论文生产线的**诊断工具**，不是必经环节。在论文初稿完成（环节5）后、论证评估（环节6）前后、甚至修改多轮仍感觉不对时，均可触发。

**核心思路**：把论文打散到段落级元素，分别将"论文本身"和"研究问题"各视为一个系统，各自做五要素分析，然后对照检验——论文的结构是否真正映射了研究问题的内在逻辑？

**与环节6的区别**：
- 环节6（论证评估）检查的是"论证是否有力"——从前提到结论的支撑力度
- 本技能检查的是"结构是否对位"——论文的骨架是否真正对应问题的骨架

**与环节3的区别**：
- 环节3（提纲审查）在写作前检查提纲的结构合理性
- 本技能在写作后（或修改中）从系统论视角做整体诊断，可能发现环节3无法发现的结构性错位

> **有条件触发**：不是每次写作都需要系统诊断。典型触发场景见下文"触发条件"。

---

## 触发条件

满足以下任一条件时，建议触发本技能：

| 触发场景 | 说明 |
|----------|------|
| 环节6评分不高 | 综合评分3.0-3.4（通过但不高），且薄弱环节集中在"论证逻辑严密性"和"学术增量贡献度" |
| 用户直觉不安 | 用户感觉"哪里不对但说不清楚"——论文看起来完整，但总觉得结构有问题 |
| 多轮修改未果 | 论文修改多次（≥3轮），每次修完仍不满意，说明可能是结构性问题而非局部问题 |
| 结构性调整前 | 准备做大规模结构调整（合并章节/重写某章）前，先做系统诊断确认调整方向 |
| 用户主动调用 | 用户明确要求做系统诊断 |

> **不触发的情况**：环节6综合评分≥3.5且用户满意时，不需要触发本技能。

## 核心方法论

### 双系统对照诊断

将两个对象分别视为系统，各自做五要素分析，然后对照：

**系统A：论文本身（载体系统）**

| 要素 | 分析问题 |
|------|----------|
| **环境** | 论文所处的学术环境是什么？对话的是哪些文献？回应的是什么实践问题？ |
| **边界** | 论文讨论的范围边界在哪里？哪些纳入了讨论、哪些被排除？边界是否清晰？ |
| **功能** | 论文要实现什么功能？是解释、批判、建构还是建议？功能是否单一明确？ |
| **结构** | 论文的章节如何组织？各章节之间是什么关系（递进/并列/总分）？结构是否服务于功能？ |
| **演化** | 论文从初稿到当前版本经历了哪些修改？修改的方向是什么？是否在收敛还是发散？ |

**系统B：研究问题（内容系统）**

| 要素 | 分析问题 |
|------|----------|
| **环境** | 这个问题在什么背景下产生？受哪些因素影响？问题的环境与论文描述的环境是否一致？ |
| **边界** | 问题的边界在哪里？哪些是这个问题的子问题、哪些是相邻问题？边界是否与论文的讨论边界匹配？ |
| **功能** | 解决这个问题能带来什么？是理论推进还是实践改善？功能与论文声称的功能是否对位？ |
| **结构** | 问题本身的结构是什么？有哪些层面/维度/要素？问题的内在结构与论文的章节结构是否映射？ |
| **演化** | 这个问题是如何演变来的？历史脉络如何？论文是否回应了问题的演化趋势？ |

### 对照检验

将系统A和系统B的要素逐一对照：

```
环境对照：论文的学术环境是否覆盖了问题所处的全部相关环境？
  → 如不覆盖：论文可能遗漏了重要对话对象
  → 如过度覆盖：论文可能跑题

边界对照：论文的讨论边界是否与问题的真实边界匹配？
  → 论文边界<问题边界：讨论不充分，遗漏了关键维度
  → 论文边界>问题边界：跑题，讨论了不属于本问题范畴的内容
  → 边界错位：论文讨论了问题的某个侧面，但问题的主要矛盾在另一侧面

功能对照：论文实现的功能是否是解决这个问题需要的功能？
  → 如不对位：例如问题需要"建构"但论文做的是"批判"——功能错位

结构对照：论文的章节结构是否映射问题的内在结构？
  → 如不映射：论文按自己的逻辑组织，但问题的内在逻辑不同——这是最核心的诊断
  → 典型症状：问题的某个关键维度在论文中没有被专门讨论，或被分散在多个章节

演化对照：论文是否回应了问题的最新演化？
  → 如未回应：论文可能在讨论一个已经变化了的问题的旧版本
```

### 上层抽象验证（可选，需与用户确认）

> **重要**：上层抽象不是机械地找上位概念，而是逻辑/哲学层面的抽象。有时抽象不好，需要跟用户确认抽象方向。

当感觉研究问题"说得不够透"时，可以尝试将当前研究问题向上推一层：

```
当前问题 → 这是一个什么更高层次问题的子问题？
  → 那个更高层次的问题有什么特征？
  → 当前问题与更高层次问题的关系是什么？
  → 从更高层次回头看当前问题，是否有遗漏的维度？
  → 抽象是否成立？是否过度抽象？是否抽象到了不相关的层面？
```

**举例**：
- 当前问题：法务工作面临哪些法律风险？
- 上层抽象：法务是法律使用者之一，法律使用者群体面临哪些共性问题？
- 回到子问题：法务作为法律使用者的一个子类，有哪些独特的场景和描述不同于其他法律使用者？

**注意事项**：
1. **抽象方向不唯一**——同一个问题可以从不同角度向上抽象，需要判断哪个角度对论文最有价值
2. **抽象可能失败**——有时抽象出来的上位问题与当前问题关联不大，或者过于抽象失去了指导意义
3. **必须与用户确认**——AI提出抽象方向建议，由用户判断是否采用。不要自行决定抽象方向
4. **不是每次必做**——只有当感觉问题说得不够透彻时才启用

## 执行流程

### 阶段一：元素拆解

```
步骤1：将论文打散到段落级
  - 每一段是一个元素
  - 关系连接紧密的段落组成一个组分
  - 记录每个组分的功能和论证目标

步骤2：提取论文的系统要素（系统A）
  - 环境：论文对话的文献、回应的实践
  - 边界：讨论范围
  - 功能：论文要做什么
  - 结构：章节组织方式
  - 演化：修改历程（如有）

步骤3：提取研究问题的系统要素（系统B）
  - 环境：问题产生的背景
  - 边界：问题的范畴
  - 功能：解决问题的价值
  - 结构：问题的内在维度
  - 演化：问题的发展脉络
```

### 阶段二：双系统对照分析

```
步骤4：五要素逐一对照
  - 环境对照 → 标记：对齐 / 不对齐（说明）
  - 边界对照 → 标记：匹配 / 不匹配（说明）
  - 功能对照 → 标记：对位 / 错位（说明）
  - 结构对照 → 标记：映射 / 不映射（说明）
  - 演化对照 → 标记：回应 / 未回应（说明）

步骤5：识别断裂点
  - 哪些对照结果不理想？
  - 不理想的原因是什么？（论文的问题 vs 问题本身的问题）
  - 严重程度如何？
```

### 阶段三：上层抽象验证（可选）

> **触发条件**：步骤5发现"结构对照"不映射，或用户感觉"问题说得不够透"。

```
步骤6：提出抽象方向建议
  - AI提出2-3个可能的抽象方向
  - 每个方向附简要说明

步骤7：与用户确认抽象方向
  - 向用户说明：这是逻辑/哲学层面的抽象，不一定能抽象好
  - 由用户选择或修正抽象方向
  - 如用户认为不需要抽象 → 跳过本阶段

步骤8：执行抽象验证
  - 从上层问题回看当前问题
  - 检查是否有遗漏维度
  - 检查逻辑是否有错误
  - 如发现遗漏或错误 → 记录
```

### 阶段四：断裂诊断与结构重置建议

```
步骤9：综合诊断
  - 汇总所有断裂点
  - 判断严重程度（结构性错位 / 局部错位 / 基本对齐）
  - 判断回退级别

步骤10：输出结构重置建议
  - 如为结构性错位 → 建议回退到环节2（思路梳理）或环节3（提纲审查），重新设计框架
  - 如为局部错位 → 建议在环节5层面调整（合并/拆分/移动章节）
  - 如基本对齐 → 标记可继续推进，列出微调建议

步骤11：如需结构重置
  - 提出新的结构建议
  - 说明新结构如何解决断裂问题
  - 由用户确认是否执行重置
```

## 回溯协议

本技能的诊断结果可能触发以下回退：

| 诊断结论 | 回退到 | 说明 |
|----------|--------|------|
| 结构性错位（系统A结构与系统B结构完全不映射） | 环节2（思路梳理） | 需要重新梳理论证框架，可能需要重新确定核心命题 |
| 边界严重不匹配 | 环节2（思路梳理） | 需要重新界定问题边界 |
| 功能错位 | 环节2（思路梳理） | 需要重新明确论文要做什么 |
| 局部结构错位 | 环节3（提纲审查） | 需要调整提纲的章节结构 |
| 演化未回应 | 环节4（文献检索） | 需要补充最新文献 |
| 基本对齐 | 不回退 | 继续推进，按微调建议修改 |

> **重要**：回退决定由用户做出。AI提出建议，用户确认后执行。参见orchestrator中的"用户判断优先规则"。

## 与其他技能的协作

| 协作方向 | 技能 | 关系 |
|----------|------|------|
| 上游 | paper-argument-evaluator（环节6） | 环节6评分不高时触发本技能 |
| 上游 | paper-writing-engine（环节5） | 论文初稿是本技能的输入 |
| 下游 | paper-idea-architect（环节2） | 如需结构重置，回退到环节2 |
| 下游 | paper-outline-reviewer（环节3） | 如需调整提纲，回退到环节3 |
| 互补 | systems-thinking | 系统思维技能提供方法论支撑，本技能是其论文场景的具体应用 |

## 数据接口

**输入**：
- 论文初稿（环节5输出）
- 标准化论证框架文档（环节2输出，用于对照问题边界）
- 论文学证强度评估报告（环节6输出，如有——用于判断是否触发）

**输出**：
- 论文系统诊断报告

---

## 输出底线

- **不替用户做方向性判断**——抽象方向、结构重置方案、回退决定，均需用户确认
- **诊断必须具体**——不说"结构有问题"，说"第二章讨论的是问题的历史维度，但问题的核心矛盾在规范维度，论文缺少专门的规范维度章节"
- **对照必须落地**——每项对照结果必须引用论文具体段落和问题具体维度
- **不夸大断裂**——如只是局部错位，不说成结构性错位
- **不隐瞒断裂**——如发现结构性错位，即使论文看起来完整，也必须如实报告
- **抽象验证必须与用户确认**——AI不自行决定抽象方向
